# 작업계획서 · 결과보고서

## A. 착수 전 — 작업계획서
1. `docs/ROADMAP.md`의 해당 항목과 관련 `docs/decisions/`를 확인한다 (이미 보류·폐기 결정된 것인지).
2. 아래 양식으로 작성해 보여주고 **사용자 확인을 받은 뒤** 진행한다.

```
## 작업계획서

### 작업 개요
- 작업명: (한 줄 요약)
- 목적: (왜 필요한가)
- 예상 소요 시간:

### 현재 상태 (AS-IS)
- 현재 동작과 문제점

### 변경 후 상태 (TO-BE)
- 작업 후 달라지는 점

### 작업 범위 (변경할 파일 목록)
| 파일 | 변경 유형 | 변경 내용 요약 |
|------|-----------|----------------|

### 단계별 작업 순서
1. 1단계: (무엇을, 왜)

### 주의사항 / 리스크
- (API 키 필요, 서버 재시작 필요(index.html 수정 시), 유료 호출, 데이터 포맷 변경 등)

### 롤백 방법
- (예: git revert <커밋>)
```

3. 승인되면 ROADMAP "진행 중" 표에 한 줄 추가한다 (worktree 병렬 작업 중이면 생략 — main 병합 때 처리).

## B. 완료 후 — 검증 → 기록 → 보고서 → 커밋 → 푸시 확인

### 1) 검증
- 화면이 바뀌는 작업은 **`stockview-verify` 스킬**로 API 점검 + Playwright 캡처를 먼저 한다.
- 테스트 결과에는 **직접 확인한 것만** 체크한다.

### 2) 기록 (커밋에 같이 포함)
- `docs/CHANGELOG.md`: 해당 월 섹션 **맨 위**에 `- MM-DD | 구분 | 내용 | 커밋` 한 줄. Phase 번호를 새로 쓰면 맨 위 "누적 요약"도 갱신. 커밋 해시는 커밋 후 채우거나 `(이번 커밋)`으로 적는다.
- `docs/ROADMAP.md`: 끝난 항목 삭제, 새로 생긴 후보·보류 항목 추가.
- 구조가 바뀌었으면(새 API·스케줄러·데이터 파일) `docs/architecture.md` 해당 표 갱신.
- 되돌리기 어려운 결정(기술 선정, 보류·폐기)을 했으면 `docs/decisions/NNN-제목.md` 추가.

### 3) 결과보고서

```
## 작업 결과 보고서

### 작업 요약
- 작업명:
- 완료 일시: (YYYY-MM-DD)
- 결과: ✅ 성공 / ⚠️ 부분 성공 / ❌ 실패

### 완료된 작업 내용
| 파일 | 변경 유형 | 변경 내용 |
|------|-----------|-----------|

### 테스트 결과
- [x] (직접 확인한 것만)
- [ ] (미확인 항목은 체크 해제 + 이유)

### 주요 변경사항 설명 (초보자용)
- 전문 용어 없이 쉽게

### 알려진 이슈 / 다음 작업 제안
- (없으면 "없음")

### 푸시 대기 중인 커밋 (N개)
- (git log origin/main..HEAD --oneline 결과)
→ GitHub에 올릴까요?
```

### 4) 커밋
- 메시지: `feat:` / `fix:` / `refactor:` / `chore:` / `docs:` + 한글 요약. 성격이 다른 변경은 커밋을 나눈다.
- `git add`는 파일을 지정해서 한다 (`-A` 지양). `data/pe_eps_cache.json`은 기능 커밋에 섞지 않는다.
- `api/`, `.env`, 키 파일이 스테이징되지 않았는지 `git status`로 확인한다.

### 5) 푸시 — 반드시 확인 후
- 보고서 끝 "푸시 대기 중인 커밋"을 보여주고 **사용자가 승인할 때만** `git push`한다. 자동 푸시 금지.
- 이유: 저장소가 공개 상태이고, Render가 연결돼 있으면 main 푸시가 곧 배포가 될 수 있다.
